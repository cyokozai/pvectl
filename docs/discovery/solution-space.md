# Solution Space — 差別化の確立

- **作成**: 2026-09-22
- 前提: [problem-space.md](problem-space.md) / [ADR-005](../adr/ADR-005-purpose-and-non-goals.md)

## 1. ポジショニング（採用導線で使う 1 文）

> **Terraform は Proxmox を「構築する」ツール、pvectl は Proxmox を「運用する」ツール。**

補助となる 2 文目（README の Why に置く粒度）:

> pvectl は、state ファイルを持たない宣言的収束と、命令的な運用動詞を、1 つのバイナリで手元から実行する CLI。
> **マニフェストに書いていないフィールドは存在しない**——だからサーバー既定値もクローン継承値も差分として現れず、既存 VM を 1 台ずつ、1 フィールドずつ管理下に移せる。

**言ってはいけないこと**: 「Terraform より軽量」「Terraform の代替」。P4（共存ターゲット）を敵に回し、しかも J1 単体では勝てない土俵で戦うことになる。差は軽さではなく**所有権モデル**である。

## 2. 差別化の 4 本柱

| # | 柱 | 何が違うか | Terraform 側が同じことをできない理由 | 効くペルソナ |
|---|---|---|---|---|
| **D1** | **宣言キーのみを管理する** | 比較・更新は宣言したキーだけ。書いていないものは差分にならない | スキーマが「宣言されたか」と「空か」を区別できない。bpg は `proxmox_cloned_vm`（EXPERIMENTAL、cloud-init 等を除外）で近似するのが限界 | P1 / P2 |
| **D2** | **state ファイルを持たない** | サーバーが唯一の真実。壊れる state も、ロックも、import も無い | tfstate は Terraform のモデルの前提であり外せない | P1 / P2 |
| **D3** | **宣言と命令が同じバイナリに載る** | `apply` / `diff` と `start` / `stop` / `exec` / `migrate` が同居。持続する状態は `spec.runStrategy`、1 回限りは動詞 | 1 回限りの操作を「望ましい状態」として表現できない。`null_resource` / provisioner に逃げるしかない | P1 / P3 |
| **D4** | **live → マニフェストの export**（未実装・§5） | 「export の出力をそのまま apply して全件 `unchanged`」を正しさの定義とする | `terraform import` は state に取り込むだけで、HCL は人が書く。bpg / Telmate / Kubemox のいずれも一級機能を持たない | **P2** |

D1〜D3 は v0.1.0 で実現済み。**D4 だけが未実装であり、かつ最大の空き地。**

## 3. Terraform が勝つ領域（降りる場所を先に決める）

差別化は「勝てない場所を言えること」で信頼性が決まる。以下は README にも書いてよい。

| 領域 | Terraform が勝つ理由 |
|---|---|
| 複数プロバイダ横断の依存グラフ（DNS・証明書・クラウド） | pvectl は Proxmox しか知らない |
| 大量生成（`for_each` / モジュール / 変数） | YAML に生成表現がない。テンプレート化は外部ツールに出る |
| 一括破棄（`destroy`） | `--prune` は非目標。所有権表明の設計が未了 |
| 同時 apply の調停 | state を持たない = ロックを持たない |
| plan 承認ワークフローのエコシステム（Atlantis / TFC） | pvectl は exit code 契約のみを提供する |

## 4. Lean Canvas（Customer Segments と Unfair Advantage に限定）

| 枠 | 内容 |
|---|---|
| **Customer Segments** | P2（手で育ったクラスタを持つ小規模チーム）を**主**、P1 を早期採用者、P3 を入口、P4 を共存ターゲットとする |
| **Problem** | J2 取り込みの手段が市場に存在しない。IaC 化は「最初の 1 歩」で止まっている |
| **Unique Value Proposition** | 既存クラスタを壊さずに、1 台ずつ、1 フィールドずつ宣言的管理へ移せる唯一の手段 |
| **Unfair Advantage** | 所有権モデルが**構造的**に Terraform のスキーマで表現できないこと。追随するには別リソース + experimental という形しか取れず、既存リソースの意味論を壊せないため一様には適用できない |
| **Channels** | GitHub Release / README / Proxmox コミュニティ。Homelab 系の口コミ |
| **Cost / Revenue** | 収益化しない個人 OSS。費用はメンテナの時間のみ |

## 5. North Star Metric

個人 OSS であり、利用実態を直接計測できない。**代理指標であることを明示したうえで**次を置く。

> **NSM: 「export → apply が全件 `unchanged`」を達成したクラスタの報告数**

- 内部の先行指標: 自分のクラスタで手動 UI 操作ゼロの連続日数（現行 PRD §7 を継続）
- 外部の代理指標: リリース DL 数ではなく、**実運用に言及した issue / discussion の件数**（DL は試用と区別できない）
- 3 ヶ月後（2026-12 目安）の定義: 自分以外の 1 クラスタで上記の unchanged が報告されること。1 件で足りる——P2 の入口が通ったことの証明になるため

## 6. ロードマップ判定基準（ペルソナ由来）

機能提案の受け入れは ADR-005 の 2 問（宣言キーのみの原理に収まるか / 持続する状態か）で判定する。**そこを通ったものの優先順位**を、ペルソナで決める。

| 判定 | 規則 |
|---|---|
| 最優先 | **P2 の入口を開けるもの**（= D4 export とその e2e 保証） |
| 次点 | P1 の信頼獲得点（再 apply の `unchanged`、diff の exit code）を壊さない保守・回帰 |
| 通常 | P3 の運用動詞の拡充、新 kind（M2 以降） |
| 非採用 | 非ターゲット層（大量生成・一括破棄・同時実行調停）のためだけの機能 |

### 帰結: M2（LXC）と export の順序に論点がある

現行 PRD は `v0.2.0` = M2（LXC）。だがペルソナ分析からは **export のほうが先**という結論が出る。

| | export を先に | M2（LXC）を先に |
|---|---|---|
| 効く相手 | P2（未獲得の層・入口が塞がっている） | 既存 P1 / P3 の適用範囲拡大 |
| 差別化への寄与 | D4 を実在させる。唯一の空き地を押さえる | 競合も持つ領域（bpg は LXC 対応済み） |
| 実装の土台 | `get -o yaml` の round-trip が単体テストで通っている（`apply_test.go` の `TestGetYAMLRoundTrip`） | `FindGuest` の一般化が必要 |
| 逆に言えば | LXC 未対応は「まだ VM だけ」と説明できる | export 不在は「IaC 化の入口が無い」ままになる |

**推奨**: `v0.2.0` を export（+ e2e 保証）、`v0.3.0` を LXC に入れ替える。ADR-005 §5 の決定は既に有効であり、未定なのは実装時期だけなので、ADR の撤回は不要——PRD のマイルストーン順の変更で足りる。**これはユーザー判断の論点として残す。**
