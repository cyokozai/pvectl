# ADR-007: ビルドツール — GNU make を維持し、発見性だけを補う

- **状態**: 採用（2026-09-16）
- **決定**: タスクランナーを Task / mage / just へ移行せず、**GNU make を維持する**。make の弱点である「何ができるか分からない」は `make help` を既定ターゲットにすることで現状の枠内で解消する

## 文脈

Makefile を just などの新しいタスクランナーへ置き換えるべきかという問いに対し、2026-09 時点の一次情報（各プロジェクトのリリースページとリポジトリ直下のビルド定義）を調べた。

### 候補の比較

| ツール | 最新版 | Go OSS での採用実績 |
|---|---|---|
| **GNU make** | 4.4.1 | kubernetes / docker/cli / helm / prometheus / cilium / istio / terraform / fzf / golangci-lint / act / pulumi / cosign / containerd / grpc-go — 大規模 Go OSS はほぼ全てこれ |
| Task (go-task) | v3.53.1（2026-08-18） | goreleaser / bubbletea の 2 件のみ確認 |
| mage | v1.17.2（2026-04-23） | Hugo のみ。2023-05 から 2026-03 まで 2 年 10 ヶ月のリリース空白があり、休眠から復帰したばかり |
| just | 1.58.0（2026-08-03） | 大規模 Go OSS での採用はゼロ |

Task と just はどちらも活発に開発されており、ツール単体の品質が理由で外れるわけではない。判断を決めたのは、このリポジトリの現状との噛み合わせである。

### このリポジトリの現状

- Makefile は 10 ターゲット。`build` / `test` / `race` / `lint` / `fmt` / `vet` / `check` / `clean` / `dev-up` / `dev-down` であり、**全てが `docker compose exec dev <cmd>` の薄いラッパー**（ADR 外だが `dev-container` 前提の運用）
- CI（`.github/workflows/ci.yaml`）は Makefile を経由せず `go` コマンドを直接呼んでいる
- メンテナは 1 名、外部コントリビュータはまだ 0 人
- `make` は README / USAGE.md / `docs/dev-process.md` から参照されている

## 決定内容

GNU make を維持する。理由は 4 つ。

### 1. 追加インストールを求めない

make は Linux / macOS に最初から入っている。Task / mage / just はいずれも別途導入が必要で、`go install` か Homebrew か配布バイナリのいずれかを踏ませることになる。コントリビュータが 0 人の段階で最初の一歩に導入作業を足すのは、得るものに対して摩擦が大きい。

### 2. 移行を正当化する複雑さが無い

Task の YAML による構造化（依存・変数・ファイル監視）や mage の Turing 完全性が効くのは、タスクが分岐やループを持ち始めてからである。現状は 1 行のコマンドを 10 個並べただけで、**移行してもファイル形式が変わるだけ**で読みやすさは改善しない。

### 3. CI 側の利得が無い

CI は `go` コマンドを直接呼ぶ設計なので、タスクランナーを替えても CI の記述は 1 行も変わらない。ランナー上で新しいツールを導入するステップが増えるだけである。

なお、ビルド定義を Makefile と CI に二重に持つと version 情報の注入（`internal/cmd` の `Version` / `GitCommit` / `BuildDate`）が食い違い、手元のバイナリと配布物で `pvectl version` の出力が変わる。**`LDFLAGS` の定義箇所は Makefile 1 箇所に保ち、CI からはターゲットを呼ぶ**形を原則とする。これは make を維持するかどうかとは独立に守るべき制約だが、make を維持する限り CI から `make <target>` を呼ぶだけで満たせる。

### 4. 文書の書き換えコストが利得を上回る

README / USAGE.md / `docs/dev-process.md` の全ての `make` 参照を書き換える必要がある。文書と実際のコマンドがずれた瞬間に入門の導線が壊れるため、この書き換えは機械的ではなく検証を伴う。

### 維持したうえで補うこと

調査で見えた make の弱点のうち、**発見性の低さ**（Makefile を開くまで何ができるか分からない）は現状の枠内で解消できるので、そうする。

- `make`（引数なし）で `help` が出るよう `.DEFAULT_GOAL := help` を設定する
- ヘルプは**ターゲット名をハードコードせず、`## 説明` コメントが付いた行を走査して組み立てる**。以後追加されるターゲットはコメントを書けば自動で一覧に載る
- コンテナ未起動時の `service "dev" is not running` を、`make dev-up` を案内するエラーに差し替える

もう一つの弱点である **Windows での不安定さ**（`make` が標準で入っておらず、タブ依存の文法が CRLF で壊れる）は、現状の開発が DevContainer と macOS / Linux を前提としているため対処しない。下記の再検討条件に回す。

## 再検討の条件

この決定は永久ではない。**次のいずれかが起きたら、この ADR を改訂して再評価する。**

| 兆候 | なぜ判断が変わるか |
|---|---|
| Makefile のターゲットが **30 を超えた** | 1 行ラッパーの列挙では見通しが立たなくなり、Task の名前空間・依存記述や mage の関数分割が実際に効き始める |
| ターゲットに**条件分岐・ループ・エラーハンドリングが入り始めた**（シェルの `if` / `for` がレシピに 3 箇所以上） | make のレシピはシェル片の寄せ集めで、この段階からは mage の Go コードや Task の構造の方が読める |
| **Windows ネイティブでの開発**をサポートする必要が出た（DevContainer / WSL 前提を外す） | make の前提が崩れる。just は単一バイナリで Windows でも同じ挙動をするため第一候補になる |
| **CI が Makefile 経由になった**（ジョブが `make <target>` を呼ぶ形に変わった） | 定義の一元化という利得が生まれるため、ランナー上での導入コストと釣り合うか再計算する必要がある |
| コントリビュータから **`make` が動かない**という報告が実際に出た | 「最初から入っている」という前提が反証される。理由 1 が成立しなくなる |
| Task または just が**大規模 Go OSS に採用され始めた** | 新規コントリビュータにとっての馴染みの差が縮まり、理由 1 の重みが下がる |

逆に、**これらが起きていない限り移行は検討しない**。ツールの新しさ、構文の好み、他言語コミュニティでの流行は再検討の理由にしない。

## 結果

- ✅ コントリビュータに追加インストールを求めずに済む
- ✅ `make` 単体でターゲット一覧が出るため、Makefile を読まなくても入口が分かる
- ✅ 移行に伴う文書の一括書き換えが発生しない
- ⚠️ `## 説明` コメントは機械的に強制できない。コメントを書き忘れたターゲットはヘルプから漏れる。ターゲット追加時のレビュー項目として扱う
- ⚠️ Windows ネイティブでの開発は引き続きサポート外。DevContainer / WSL を案内する
- ⚠️ ヘルプの体裁は awk のワンライナーに依存する。凝った整形を足したくなったら、それは Makefile が複雑化している兆候として上記の再検討条件と併せて読む

## 却下した代替案

- **Task (go-task) へ移行**: YAML による構造化は魅力だが、現状の 10 個の 1 行ターゲットに構造化の対象が無い。Go OSS での採用も goreleaser / bubbletea に限られ、新規コントリビュータにとっての馴染みで make に劣る
- **mage へ移行**: ビルド定義を Go で書けるため型検査が効くが、2023-05 から 2026-03 まで 2 年 10 ヶ月のリリース空白があり、休眠から復帰したばかりで継続性を前提にできない。加えて、ビルド定義のためにパッケージとビルドタグを抱えるのは 10 ターゲットには過剰
- **just へ移行**: 構文は Makefile より素直でタブ依存も無いが、大規模 Go OSS での採用実績がゼロで、Go 開発者にとって初見のツールになる。単一バイナリで Windows でも動く利点は、Windows ネイティブ対応が必要になったときに効く（再検討条件に記載）
- **Makefile を廃止し `go run` / シェルスクリプトに寄せる**: `dev-up` / `dev-down` のようなコンテナ操作まで含めた入口が失われ、コマンドの一覧性も `make help` より落ちる
- **Makefile と Task を併存させる**: 同じ操作の入口が 2 つになり、どちらが正なのかが文書と乖離する。入口は 1 つに保つ

## 追補（2026-09-16）: 再検討条件「CI が Makefile 経由」の発火と評価

本文と「再検討の条件」の表はそのまま残し、以下を追記する。

**発火した事実**: PR #17（`feat/ci-hardening`、`dev` にマージ済み）により、CI の `build` ジョブが素の `go build` から `make build HOST=1` に変わり、`make cross-build HOST=1` を呼ぶ `cross-build` ジョブが新設された。本 ADR とほぼ同時に、再検討条件の 1 つが満たされた。

**再評価の結論: 維持する。** 条件は満たされたが、評価の向きは維持側に働いた。

1. CI が make を呼ぶようになったことで、make がビルド定義の単一の置き場所になった。これは Task / just へ移る動機ではなく、**make を維持する動機**である。`LDFLAGS` の定義が Makefile 1 箇所に集まり、CI はターゲットを呼ぶだけになった（「決定内容 3」で意図していた状態が実現した）
2. GitHub Actions のランナーに make は preinstalled である。Task / just はいずれも導入ステップ（`go-task/setup-task` / `extractions/setup-just`）が 1 つ増え、ランナー上の実行時間が伸びる。「追加インストールを求めない」という理由 1 の利点が、CI 側にも効くようになった

**この条件は今後トリガーとして機能しない。** 表の「CI が Makefile 経由になった」の行は 2026-09-16 に発火し、評価の結果 維持となった。以後この条件では再検討しない。残る 5 条件（ターゲット 30 超 / レシピの条件分岐 3 箇所以上 / Windows ネイティブ対応 / `make` が動かない報告 / Task・just の大規模 Go OSS 採用）は引き続き有効である。

**調査時点の推奨の記録**: 移行候補としての推奨は just ではなく Task だった（`go tool` で導入可能、Windows ネイティブ、`dotenv` 対応）。ただし同じ調査は「Makefile が `docker compose exec` の薄いラッパーだけなら移行の利得は限定的」とも述べていた。just は Rust 製で `cargo` 前提、Windows では `sh` を要する。
