# LinuxContainer (LXC)

[日本語](linuxcontainer.jp.md)

Reference for the `LinuxContainer` manifest and for what `apply` does with
it. Everything in [manifests.md](manifests.md) about declared keys, `diff`,
dry runs, `spec.runStrategy`, secrets, and `spec.raw` applies here too; this
page covers what is different for containers. The design is recorded in
[ADR-010](../adr/ADR-010-linux-container.md).

`TYPE` on the command line is `ct`, `lxc`, `linuxcontainer`, or
`linuxcontainers`:

```bash
pvectl get ct
pvectl get ct web-01 -o yaml
pvectl describe ct web-01
pvectl start ct web-01
pvectl delete ct web-01
```

## A first container

```yaml
# ct.yaml
apiVersion: pve.io/v1alpha1
kind: LinuxContainer
metadata:
  name: web-01              # the container's hostname
spec:
  targetNode: pve1
  unprivileged: true        # required
  osTemplate:
    volid: local:vztmpl/debian-12-standard_12.7-1_amd64.tar.zst
  resources:
    cores: 1
    memory: 512
  rootfs:
    storage: local-lvm
    size: 8G
  networks:
    - name: net0
      bridge: vmbr0
      ip: dhcp
```

```bash
pvectl apply -f ct.yaml --dry-run=server   # reports whether the template is there
pvectl apply -f ct.yaml
```

[examples/lxc.yaml](../../examples/lxc.yaml) lists every field with comments.

## Fields

| Field | |
|---|---|
| `metadata.name` | the hostname. There is no `spec.hostname`: one name, one identity |
| `targetNode` | required, immutable. `apply` never moves a container (use `migrate`) |
| `vmid` | optional; the next free id when omitted. Immutable |
| `unprivileged` | **required**, `true` or `false`. Create-only (see below) |
| `osTemplate` | create-only. `volid`, or `url` + `sha256` + `storage` (see below) |
| `pool` | create-only. A different pool on a later apply is an error |
| `description` | |
| `resources.cores` / `memory` / `swap` | memory and swap in MiB; `swap: 0` means no swap |
| `rootfs` | `storage` and `size`. A larger size is applied with resize; a smaller one is an error, as is another storage |
| `mountPoints[]` | `name` (`mp0`, `mp1`, …), `storage`, `size`, `path`. Same growth rules as `rootfs` |
| `networks[]` | `name` (`net0`, …), `bridge`, and optionally `interface`, `ip`, `gw`, `tag`, `hwaddr` |
| `nameserver` | |
| `features` | `nesting`, `keyctl`, `fuse`, `mknod`. Only the flags written are managed |
| `root` | `passwordFrom`, `sshKeys`. Create-only and write-only (see below) |
| `runStrategy` | `Manual` (default), `Always`, `Halted`, as for a VM |
| `tags` | |
| `raw` | flat API keys pvectl does not model, such as bind mounts |

Network sub-keys:

- `interface` defaults to `eth<N>` for slot `net<N>`. It is a default inside a
  NIC you wrote, never a NIC pvectl adds.
- `ip` is `dhcp`, `manual`, or a CIDR such as `10.0.0.50/24`.
- `tag` follows the same rule as a VM NIC: 1-4094 sets the VLAN tag, `0`
  declares "untagged" and removes a live tag, and leaving it out keeps the tag
  unmanaged.
- `hwaddr` is generated by Proxmox. It is compared only when you write it, and
  an update carries the live MAC over, so changing the bridge does not give the
  container a new MAC address.

## `unprivileged` is required

The Proxmox API creates a **privileged** container when `unprivileged` is
omitted, while the web UI defaults to unprivileged — and the choice cannot be
changed after creation. pvectl does not fill in a value the manifest does not
declare, so it asks you to write one. A manifest whose value disagrees with
the running container is an error, not a silent no-op.

`get -o yaml` always prints `unprivileged`, `false` included.

## `osTemplate`: two ways to name the template

```yaml
osTemplate:
  volid: local:vztmpl/debian-12-standard_12.7-1_amd64.tar.zst
```

uses a template that is already on the node's storage. pvectl never downloads
anything for this form. `--dry-run=server` warns when the file is not there.

```yaml
osTemplate:
  url: https://download.example.test/debian-12-standard_12.7-1_amd64.tar.zst
  sha256: <64 hex digits>
  storage: local
```

lets pvectl fetch it. The file is stored on `storage` of `targetNode` as
`pvectl-<first 16 digits of sha256>-<file name from the URL>`. Because the
digest is part of the name, a file that changed behind the same URL lands
under a new name, and a name that is already there can be trusted to hold the
declared content. The download happens only when that name is missing, and
Proxmox checks the digest itself.

- If the download fails, nothing is created. pvectl never deletes a template
  it downloaded; cleaning the storage is up to you.
- `--dry-run=server` reports that a download would happen and downloads
  nothing.
- A large template may take longer than the default `--timeout` (5m). When the
  wait runs out, the download task may still be running on the node: raise
  `--timeout` and apply again. Once the file is on the storage it is not
  downloaded again.
- The token needs `Datastore.AllocateTemplate` on the storage, and some
  Proxmox VE versions also ask for `Sys.Audit` / `Sys.Modify` on the node. A
  refused download (HTTP 403) names these privileges. The exact set has not
  been confirmed on a real node yet.

`osTemplate` states where the container came from. Proxmox does not record
it, so it is never compared on update, it is required only when the container
does not exist yet, and `get -o yaml` leaves it out. A manifest exported with
`get` applies cleanly without it.

## Root credentials

```yaml
root:
  passwordFrom: env:CT_ROOT_PASSWORD   # or file:/path/to/file
  sshKeys:
    - ssh-ed25519 AAAA... admin@example.test
```

Proxmox accepts the root password and SSH keys only at creation and does not
keep them in the config. pvectl therefore sends them once, resolves
`passwordFrom` only when it is about to create the container, and never
compares, updates, or exports them. Re-applying the manifest you created the
container with prints a warning that `spec.root` was not changed, and works
even where the secret is no longer reachable.

## Exporting

```bash
pvectl get ct web-01 -o yaml > web-01.yaml
pvectl get ct -o yaml > all.yaml
pvectl apply -f web-01.yaml      # unchanged
```

Both the named and the unnamed form round-trip: applying the output reports
`unchanged`. The table output (`get ct`, `-o wide`) reads the cluster resource
list once; the `yaml` and `json` forms of the unnamed `get` additionally read
each container's config, one API call per container.

## exec and migrate

- `exec` is not supported. Proxmox VE has no exec in its REST API for
  containers (`pct exec` only runs on the node itself); pvectl says so instead
  of trying.
- `migrate` works only while the container is stopped. `--online`, or a
  running container, is an error that tells you to stop it first.

## Not yet

- `spec.template: true` (turning a guest into a template), for VMs and
  containers alike
- the IP column in `-o wide`
- restart migration of a running container, bind mounts and device
  pass-through as typed fields (use `raw`)
